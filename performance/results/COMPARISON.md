# Transactional Outbox 전후 비교

## 결론

로컬 단일 백엔드 인스턴스와 MySQL 8.0.30, 최대 4개의 요청만 동시에 처리하는 Fake AI 환경에서 기존 방식과 Outbox 방식을 5회씩 교차 실행했습니다. 초당 20건을 5초간 요청한 결과, 기존 방식은 AI 접수 성공률이 21.03%였고 Outbox 방식은 100%였습니다.

| 지표 | 기존 방식 | Outbox 방식 |
| --- | ---: | ---: |
| 백엔드 요청 | 504 | 503 |
| 백엔드 202 | 504 | 503 |
| AI 접수 | 106(21.03%) | 503(100%) |
| AI 503 거절 | 398 | 0 |
| Webhook 성공 | 106 | 503 |
| DB 모델 FAILED | 398 | 0 |
| p95 회차 중앙값 | 933.47ms | 202.35ms |
| p95 회차 범위 | 661.99~1,371.19ms | 178.72~465.57ms |
| 최대 AI 동시 처리 | 4 | 4 |

응답 p95 중앙값은 이 실험 조건에서 약 78.3% 낮았습니다. 이는 Outbox가 언제나 단건 요청을 빠르게 만든다는 뜻이 아니라, 기존 방식에서 요청 폭주와 동시에 수행되던 외부 전송·실패 처리·DB 갱신을 Worker로 분리한 결과입니다.

## 재시도·복구 검증

- Worker 동시성 3, Fake AI 용량 2 조건에서 작업 21건을 전송했습니다.
- 실제 AI HTTP 요청 31회 중 10회가 503이었으며, 10개 이벤트가 두 번째 시도에서 성공했습니다.
- 최종적으로 Outbox `SENT` 21건, Webhook 성공 21건, 모델 `FAILED` 0건이었습니다.
- JVM 재시작 전 DB에 남긴 `PENDING` 11건은 재시작 뒤 모두 처리됐습니다.
- 동일 키 재전송 장애 주입에서는 HTTP 102회 중 중복 1회가 감지되어 고유 AI 실행은 101회로 유지됐습니다.

## 주장 가능한 범위

> 정의한 로컬 과부하 조건에서 기존 즉시 전송 방식의 하류 AI 접수 실패를 재현하고, MySQL Transactional Outbox와 동시성 제한 Worker로 요청을 DB에 보존해 AI 처리 용량에 맞춰 전달했으며, 재시도와 프로세스 재시작 복구를 확인했습니다.

다음 표현은 사용하지 않습니다.

- 대규모 트래픽을 해결했다.
- 처리량이 4.8배 또는 6배 증가했다.
- 요청 유실이 절대 발생하지 않는다.
- exactly-once를 보장한다.
- 여러 백엔드 인스턴스에서도 AI 전역 동시성 4를 보장한다.

## 한계

- 단일 PC, 단일 백엔드 인스턴스, Fake AI를 사용했습니다.
- CPU·메모리·Hikari 지표는 이번 비교에 포함하지 않았습니다.
- 실제 AI 서버의 멱등성 키 영속 처리는 별도 구현이 필요합니다.
- Outbox는 최초 분석 요청에만 적용됐습니다.
- 다중 인스턴스 선점, 이벤트 정리, 명시적 DB 마이그레이션은 후속 과제입니다.
